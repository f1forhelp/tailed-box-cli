# Online Pairing Handshake Design

This document records the recommended direction for a future online pairing milestone. It is design-only and does not implement transport, secret transmission, service management, NAT traversal, or production mesh networking.

## Goal

Define a secure initial pairing direction that lets an authorized master admit a new master or worker using a high-entropy single-use join code while preserving these existing properties:

- Join codes are for initial pairing only.
- Join codes are high entropy and generated by authorized masters.
- Plaintext join codes are not persisted.
- Used join codes cannot be reused.
- Reconnects after restart use persistent node identity, not the join code.
- Revoked nodes cannot reconnect with old credentials.
- Future transport must be designed to resist MITM.

## Non-Goals

- No production encrypted transport implementation.
- No remote command execution.
- No service management.
- No secret transmission beyond future handshake design.
- No website, MCP server, Docker, Postgres, Redis, or logging features.
- No multi-master consensus or revocation quorum.
- No external VPN, kernel VPN, OS-managed VPN config, or shelling out to networking tools.

## Threat Model

The future pairing flow should assume an attacker may observe, delay, replay, or modify network traffic. The attacker may also attempt to race a legitimate node using a stolen or copied join code.

The future design should protect against:

- Passive code disclosure from network traffic.
- MITM during first contact.
- Replay of old handshake messages.
- Reuse of consumed join codes.
- Joining the wrong network.
- Joining with the wrong role.
- Admission by an unauthorized node.
- Reconnect by a revoked node using old credentials.

The design does not protect against compromise of a master node private key, compromise of local state, or user disclosure of a join code to an attacker. Those cases require revocation, rotation, and future operational controls.

## Pairing Options

### Option A: Verifier-Only Storage With PAKE/OPAQUE-Style Pairing

The master stores verifier material derived from the join code, not the plaintext code. The joining node proves knowledge of the join code through a reviewed password-authenticated key exchange or OPAQUE-style protocol.

Pros:

- Best alignment with verifier-only persistence.
- Avoids plaintext join-code storage on the master.
- Can provide strong MITM resistance when implemented with a reviewed library/protocol.
- Good fit for the current local join-code state model.

Cons:

- More protocol complexity.
- Requires careful library selection and transcript binding.
- May add dependency and interoperability considerations.

### Option B: Noise Handshake With Join Code As PSK

The join code is used as a pre-shared secret input to a Noise-style handshake. The resulting session binds both node identities and network metadata.

Pros:

- Simple conceptual fit with future Noise-style UDP transport.
- Low overhead.
- Can bind identities and network metadata into a single transcript.

Cons:

- Straight PSK usage generally requires access to the secret, not only verifier material.
- Persisting encrypted or recoverable join-code secret material would make local state more sensitive.
- More risk of weakening the current no-plaintext-persistence property if implemented carelessly.

### Option C: Out-of-Band Master Fingerprint Plus Noise Handshake

The joining node verifies the master's long-term identity fingerprint out of band, then uses a Noise-style authenticated handshake with join authorization bound into the transcript.

Pros:

- Reduces MITM risk when users verify the master fingerprint correctly.
- Fits future persistent identity model.
- Avoids relying only on the join code as a shared secret.

Cons:

- Human verification can be skipped or performed incorrectly.
- Does not by itself solve verifier-only join-code proof.
- UX must be designed carefully to avoid training users to ignore fingerprints.

## Recommended Direction

Use Option A as the preferred future pairing design: verifier-only storage with a reviewed PAKE/OPAQUE-style protocol. Keep Option C as a supporting UX requirement for displaying and verifying master identity fingerprints. Avoid Option B unless a future design can preserve the no-plaintext-persistence goal without storing recoverable join-code secret material.

The first implementation milestone should still be small:

- Select and evaluate a reviewed Go PAKE/OPAQUE-style library or protocol package.
- Prototype local in-memory handshake tests only.
- Bind network ID, expected role, issuing master ID, joining node ID, and public key material into the authenticated transcript.
- Consume the join code atomically only after the handshake succeeds and admission metadata is persisted.
- Do not build UDP production transport in the pairing milestone unless explicitly chosen later.

## Transcript Binding Requirements

The future pairing transcript must include:

- Protocol name and version.
- Network ID.
- Join-code record ID or verifier identifier.
- Expected joining role.
- Issuing master node ID.
- Master public identity material.
- Joining node public identity material.
- Fresh ephemeral handshake public keys.
- Session ID.
- Direction labels for initiator/responder messages.

Including these values prevents a valid proof from being replayed into a different network, role, node identity, or protocol context.

## State Transition

Future successful pairing should perform one atomic local transition on the master:

- Verify the join proof.
- Confirm record is unused.
- Confirm expected network and role.
- Confirm issuing master authorization.
- Persist the new peer record.
- Mark the join code consumed.
- Reject any later attempt with the same code.

If peer persistence fails, the code should remain unused. If code consumption fails, the peer should not be considered admitted. The implementation should avoid split state.

## Open Questions

- Which reviewed Go PAKE/OPAQUE-style library should be used, if any?
- What exact master fingerprint UX should CLI and TUI display?
- Should a future master sign join-code authorization records?
- How should multi-master admission and revocation propagation work?
- What recovery process is safe when a master is lost or compromised?
- Should rejoining after revocation always require fresh identity, or should a future membership-epoch model support explicit re-admission?

## Testing Requirements For Future Pairing

Future tests should cover:

- Successful local handshake proof.
- MITM transcript tampering rejection.
- Wrong network rejection.
- Wrong role rejection.
- Wrong master rejection.
- Wrong joining node identity rejection.
- Replay rejection.
- Already-consumed code rejection.
- Atomic consume/admit behavior.
- No plaintext join-code persistence.
- No join code in logs or context files.
